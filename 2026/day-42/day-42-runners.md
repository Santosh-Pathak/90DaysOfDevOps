# Day 42 – Runners: GitHub-Hosted & Self-Hosted

## Task 1: GitHub-Hosted Runners — `.github/workflows/multi-os.yml`

```yaml
name: Multi-OS Jobs

on: [push]

jobs:
  ubuntu:
    runs-on: ubuntu-latest
    steps:
      - name: Print runner info
        run: |
          echo "OS: $RUNNER_OS"
          echo "Hostname: $(hostname)"
          echo "User: $(whoami)"

  windows:
    runs-on: windows-latest
    steps:
      - name: Print runner info
        run: |
          echo "OS: $env:RUNNER_OS"
          echo "Hostname: $env:COMPUTERNAME"
          echo "User: $env:USERNAME"

  macos:
    runs-on: macos-latest
    steps:
      - name: Print runner info
        run: |
          echo "OS: $RUNNER_OS"
          echo "Hostname: $(hostname)"
          echo "User: $(whoami)"
```

All 3 jobs run in parallel. Windows uses PowerShell syntax; Linux and macOS use bash.

### What is a GitHub-hosted runner?

A GitHub-hosted runner is a virtual machine spun up by GitHub on demand to execute a workflow job. GitHub manages the VM — provisioning, patching, and teardown. Each job gets a fresh, clean environment. They are available in Ubuntu, Windows, and macOS flavours.

## Task 2: Pre-installed Tools — ubuntu-latest

```yaml
name: Tool Versions

on: [push]

jobs:
  tool-check:
    runs-on: ubuntu-latest
    steps:
      - name: Print pre-installed versions
        run: |
          docker --version
          python3 --version
          node --version
          git --version
```

Full software list: https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md

### Why does it matter that runners come pre-installed?

You skip setup steps for common tools, keeping workflows fast and simple. No need to install Docker, Python, Node, or Git — they're ready immediately. This also means your pipeline is less likely to break due to a failed install step.

## Task 3: Self-Hosted Runner Setup (Linux)

```bash
# 1. Create a directory for the runner
mkdir actions-runner && cd actions-runner

# 2. Download the runner package (get exact URL from GitHub Settings → Runners → New runner)
curl -o actions-runner-linux-x64.tar.gz -L \
  https://github.com/actions/runner/releases/download/v2.x.x/actions-runner-linux-x64-2.x.x.tar.gz
tar xzf ./actions-runner-linux-x64.tar.gz

# 3. Configure (token is generated by GitHub — copy from the UI)
./config.sh --url https://github.com/YOUR_USERNAME/YOUR_REPO --token YOUR_TOKEN

# 4a. Run interactively
./run.sh

# 4b. OR install as a persistent background service
sudo ./svc.sh install
sudo ./svc.sh start
```

**Verify:** Go to repo → Settings → Actions → Runners. Your runner should show with a green dot and status **Idle**.

## Task 4: Use the Self-Hosted Runner — `.github/workflows/self-hosted.yml`

```yaml
name: Self-Hosted Job

on: [push]

jobs:
  on-my-machine:
    runs-on: self-hosted
    steps:
      - name: Print hostname
        run: hostname

      - name: Print working directory
        run: pwd

      - name: Create a proof file
        run: echo "CI ran here at $(date)" > /tmp/ci-proof.txt

      - name: Verify file exists
        run: cat /tmp/ci-proof.txt
```

**Verify locally after the run:**
```bash
cat /tmp/ci-proof.txt
# CI ran here at Mon Apr 20 12:34:56 UTC 2026
```

## Task 5: Labels

Add a label in GitHub → Settings → Actions → Runners → click your runner → add label `my-linux-runner`.

Then update the workflow:

```yaml
jobs:
  labeled-job:
    runs-on: [self-hosted, linux, my-linux-runner]
    steps:
      - name: Confirm labeled runner picked it up
        run: echo "Running on labeled runner: $HOSTNAME"
```

### Why are labels useful?

When you have multiple self-hosted runners (e.g. one with a GPU, one for ARM builds, one in a production subnet), labels let you route specific jobs to specific machines. Without labels, GitHub picks any available self-hosted runner at random.

Common label patterns:
- `[self-hosted, linux, gpu]` — GPU machine for ML jobs
- `[self-hosted, linux, prod]` — runner inside the production VPC
- `[self-hosted, arm64]` — ARM build machine

## Task 6: GitHub-Hosted vs Self-Hosted

| | GitHub-Hosted | Self-Hosted |
|---|---|---|
| Who manages it? | GitHub | You |
| Cost | Free tier (2,000 min/month), then paid per-minute | Free (you pay for your own infra/VM) |
| Pre-installed tools | Rich toolset: Docker, Python, Node, Go, Java, Git, etc. | Only what you install yourself |
| Good for | Open-source projects, standard builds, quick CI | Private infra, custom hardware, GPU, long-running jobs, VPC-restricted resources |
| Security concern | Ephemeral & isolated — safe for untrusted PRs | Persistent machine — never use with public repos; untrusted PRs can run arbitrary code on your server |
